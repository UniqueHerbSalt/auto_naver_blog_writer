# 블로그 글 작성 지침 (로컬 PC Claude 용)

이 문서는 **로컬 PC 에서 검색·취합·글쓰기를 담당하는 Claude** 에게 주는 지침이다.
`naver-blog-mcp` 서버가 연결된 세션에서 이 문서를 읽고 따른다.

개발(이 저장소의 코드를 짜는 일)과 실행(실제로 글을 쓰고 발행하는 일)은 다른
세션이다. 이 문서는 **실행 쪽** 을 위한 것이다.

문서는 셋으로 나뉜다. 순서대로 본다.

| 문서 | 답하는 질문 |
|---|---|
| [SOURCES.md](SOURCES.md) | **무엇에 대해 쓸까** — 소식 출처, 주제 선별 기준 |
| [STYLE.md](STYLE.md) | **어떻게 쓸까** — 글 구조, 제목, 루머 표기 |
| 이 문서 | **어떻게 올릴까** — 이미지, HTML, 발행 |

---

## 1. 너의 역할

| 너 (Claude) | MCP 서버 |
|---|---|
| **주제 선별**, 웹 검색, 출처 교차 검증 | 크로미움 기동, 로그인 세션 관리 |
| 분야별 정리, 글 작성 | HTML 파싱 → 블록 변환 |
| **이미지 내려받아 저장** | 이미지를 네이버에 업로드 |
| 제목·태그·카테고리 결정 | 에디터 조작, 임시저장, 발행 |

너는 **완성된 HTML** 을 만들어 MCP 도구에 넘긴다. 에디터를 어떻게 조작할지는
신경 쓰지 않는다. 반대로 MCP 는 글의 내용에 관여하지 않는다.

## 2. 워크플로

1. `check_auth()` — 로그인 세션부터 확인한다. 여기서 실패하면 사람이 브라우저에서
   로그인을 마쳐야 하므로, 글을 다 쓴 뒤에 발견하면 헛수고가 된다.
2. **주제를 고른다** — [SOURCES.md](SOURCES.md) 의 소스를 훑고 세 가지 질문으로
   거른다. 개발자만 관심 있는 주제는 여기서 버린다.
3. 웹 검색으로 조사한다. **출처 2곳 이상에서 교차 확인**하고, 매체 기사가
   인용한 원본(기업 뉴스룸, 보도자료)까지 거슬러 올라간다.
4. **이미지를 내려받아 로컬에 저장한다** (§3 — 가장 중요).
5. 글을 쓴다 — 구조와 문장은 [STYLE.md](STYLE.md) 를 따른다.
6. HTML 로 옮긴다 (§4). `preview_html()` 로 파싱 결과를 먼저 확인하면
   브라우저를 띄우지 않고 형식을 검증할 수 있다.
7. `create_draft(title=..., html=..., tags=[...], category=...)` 로 임시저장한다.
8. 사람에게 확인받는다. 승인 후 `publish(draft_id)`.

## 3. 이미지 — 반드시 지킬 것

### 원칙

**이미지는 네가 직접 내려받아 로컬 파일로 저장하고, HTML 에는 그 파일의
절대 경로를 넣는다.** 외부 URL 을 `<img src>` 에 그대로 두지 않는다.

```html
<!-- 이렇게 -->
<img src="/Users/me/blog-assets/2026-08-22-ios27/01-settings.png" alt="iOS 27 설정 화면">

<!-- 이러면 안 된다 -->
<img src="https://www.apple.com/newsroom/images/settings.png" alt="...">
```

### 왜 네가 받아야 하는가

- 많은 뉴스·기업 사이트가 **hotlink 차단과 User-Agent 검사**를 한다. MCP 서버가
  나중에 그 URL 을 내려받으려 하면 403 이 떨어져 이미지가 통째로 빠진다.
  브라우저 맥락에서 가져오는 네가 훨씬 안정적이다.
- 네이버는 **자사 CDN 에 업로드된 이미지만** 본문에 넣는다. 어차피 파일이
  있어야 한다. URL 을 넘기면 다운로드 단계가 뒤로 밀릴 뿐이다.
- 네가 받으면 **이미지를 실제로 보고** 글 내용에 맞는 사진인지 판단할 수 있다.
  엉뚱한 썸네일이나 광고 배너가 섞여 들어가는 것을 막는다.

### 저장 규칙

- 글마다 별도 폴더를 만든다: `./blog-assets/<YYYY-MM-DD>-<슬러그>/`
- 파일명은 `본문 등장 순서 - 내용` 으로: `01-settings.png`, `02-battery-chart.png`
- 원본 확장자를 유지한다. 변환하지 않는다.

### 어디서 가져오는가

- **원본 페이지에서 가져온다.** 애플 뉴스룸, 기업 보도자료, 공식 블로그,
  기사 본문에 실린 이미지.
- 이미지 검색 결과에서 아무거나 긁지 않는다. 출처를 되짚을 수 없는 이미지는 쓰지
  않는다.
- 출처가 불분명하면 **그냥 넣지 않는다.** 이미지 없는 글이 출처 불명 이미지가
  박힌 글보다 낫다.
- 워터마크가 박힌 타 블로그·커뮤니티 이미지는 쓰지 않는다.

### 출처 표기

이미지마다 `<figcaption>` 으로 출처를 단다.

```html
<figure>
  <img src="/절대/경로/01-settings.png" alt="iOS 27 제어센터 새 레이아웃">
  <figcaption>출처: Apple Newsroom</figcaption>
</figure>
```

`alt` 는 화면에 무엇이 보이는지 설명한다. `figcaption` 은 출처를 적는다.
둘은 다른 용도이니 같은 문장을 복사하지 않는다.

### 배치

- 소제목 하나에 사진이 몰리지 않게 본문 전반에 고르게 둔다.
- 도입부 직후에 대표 이미지 한 장이 있으면 글이 훨씬 읽힌다.
- 사진이 하나도 없는 글은 네이버에서 잘 읽히지 않는다. 최소 1장은 넣되,
  출처 규칙을 어기면서까지 채우지는 않는다.

## 4. HTML 작성 규칙

MCP 파서는 **화이트리스트** 방식이다. 아래 표에 없는 태그는 텍스트만 남고 버려진다.

| 태그 | 용도 |
|---|---|
| `<h2>` `<h3>` | 소제목. `<h1>` 은 쓰지 않는다 (제목은 별도 인자) |
| `<p>` | 문단 |
| `<figure>` `<img>` `<figcaption>` | 이미지와 출처 캡션 |
| `<blockquote cite="...">` | 인용. `cite` 에 출처 URL |
| `<ul>` `<ol>` `<li>` | 목록 |
| `<a href="...">` | 링크 |
| `<hr>` | 구분선 |
| `<strong>` `<em>` | 받아들이지만 **평문으로 눌린다** (아래 참고) |

지킬 것:

- `<div>` `<span>` `<table>` `<style>` `class` `style` 속성은 쓰지 않는다.
  스마트에디터로 넘어가면서 전부 사라진다.
- 마크다운(`**`, `#`)을 HTML 안에 섞지 않는다.
- 제목은 HTML 에 넣지 말고 `create_draft(title=...)` 인자로 넘긴다.
- 소제목 텍스트에 `[ ]` 같은 기호를 직접 넣지 않는다. 렌더링할 때 서버가 처리한다.

### 링크가 어디에 살아남는지 (중요)

| 위치 | URL |
|---|---|
| 문단(`<p>`) 안의 링크 | **버려진다.** 문구만 남는다 |
| 목록(`<li>`)·인용문(`<blockquote cite>`) 안의 링크 | 살아남는다 |
| 문단 밖에 홀로 선 `<a>` | 살아남는다 (링크 카드가 된다) |

문단 속 URL 을 버리는 이유: 본문 한가운데 생 URL 이 박히면 읽기 나쁘고,
한국어 조사가 URL 뒤에 바로 붙으면(`...ios27에서`) 스마트에디터의 자동 링크가
조사까지 삼켜 링크가 깨진다.

**그래서 출처 목록(§5)이 필수다.** 문단에서 참조한 자료는 반드시 글 말미
`<ul><li><a>` 목록에 다시 넣어야 URL 이 독자에게 남는다.

### 인라인 강조는 평문이 된다

`<strong>` `<em>` 은 파서가 받아들이지만 **굵게 표시되지 않고 평문으로 들어간다.**
에디터에서 인라인 서식을 넣으려면 타이핑 도중 단축키를 토글해야 하는데 그러면
입력이 불안정해진다. 강조하고 싶은 내용은 소제목(`<h3>`)으로 올리거나 문장을
따로 떼어 쓰는 편이 낫다.

## 5. 출처 — 정보성 글의 핵심

- 사실 하나하나가 어디서 왔는지 추적 가능해야 한다. 기억으로 쓰지 말고
  **검색해서 확인한 것만** 쓴다.
- 날짜·버전·수치는 특히 조심한다. "iOS 27 퍼블릭 베타 100" 같은 구체적 숫자는
  반드시 원문에서 확인한다.
- 확인 안 된 내용은 **빼거나**, "아직 공식 확인되지 않았다"고 명시한다.
  추측을 사실처럼 쓰지 않는다.
- **글 말미에 출처 목록을 반드시 단다.** 문단 속 링크는 URL 이 버려지므로
  (§4 참고), 이 목록이 유일하게 URL 이 살아남는 자리다.

```html
<h3>출처</h3>
<ul>
  <li><a href="https://www.apple.com/newsroom/...">Apple Newsroom — iOS 27 Public Beta</a> (2026-08-22 확인)</li>
</ul>
```

## 6. 발행

- `create_draft` 로 **임시저장까지만** 하고 멈춘다. 사람 확인 없이 `publish` 를
  부르지 않는다.
- 공개범위 기본값은 `private`(비공개)다. 공개 발행은 사람이 명시적으로 요청할
  때만 한다.
- **하루 1~2건을 넘기지 않는다.** 네이버는 자동 생성 글의 대량 발행에 민감하다
  (저품질 블로그 판정). 많이 쓰는 것보다 한 편을 제대로 쓰는 게 낫다.

## 7. 하지 말 것

- **개발자만 관심 있는 주제를 고르는 것** (SOURCES.md §1 — 가장 흔한 실패)
- 뉴스를 그대로 옮기기만 하는 것. 국내 맥락·비교·해석 중 최소 둘을 더한다
- 루머를 확정 사실처럼 쓰는 것
- 검색으로 확인하지 않은 사실을 쓰는 것
- 외부 URL 을 `<img src>` 에 그대로 두는 것
- 출처 불명 이미지를 넣는 것
- 사람 확인 없이 발행하는 것
- 이모지·기호만 있고 문장이 없는 빈 문단
- 소제목만 잔뜩 늘어놓고 각 문단은 두 줄뿐인 글. 소제목을 늘리기보다 이미 있는
  소제목 안에서 깊이 파고든다.
- "안녕하세요, 오늘은 ~에 대해 알아보겠습니다" 로 시작하는 것. 첫 문장은
  뉴스 그 자체여야 한다(STYLE.md §2).
